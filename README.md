\# STM32 Makefile-Based Multi-File C Project



An embedded C project for the \*\*STM32F407G-DISC1\*\* development board, built using a handwritten Makefile and the GNU Arm toolchain.



The application uses direct register access without HAL. Separate modules handle LEDs, button debouncing, and SysTick timing.



\## Features



\- Separate C source files and headers

\- Parallel builds using GNU Make

\- Automatic header dependency tracking

\- Incremental compilation

\- ELF, BIN, HEX, and linker map generation

\- Firmware upload and verification using `make flash`

\- PowerShell tool setup script

\- Nonblocking LED blinking and button processing



\## Hardware Behavior



| Action | Result |

|---|---|

| Power on or reset | Green LED blinks slowly |

| Press and release USER once | Green LED switches to fast blinking |

| Press and release USER again | Green LED returns to slow blinking |

| Hold USER | Blue LED stays on while held |

| Disconnect and reconnect power | Application restarts in slow mode |



Each debounced button press changes the blinking speed once, including a press that is subsequently held.

\## Pin Mapping



| Component | MCU pin |

|---|---|

| Green LED — LD4 | PD12 |

| Blue LED — LD6 | PD15 |

| USER button — B1 | PA0 |



The USER button reads high when pressed. The onboard LEDs turn on when their outputs are high.

\## Setup



Open PowerShell in the project folder and run:



```powershell

. .\\setup.ps1

```



The script defaults to this STM32CubeIDE installation:



```text

C:\\ST\\STM32CubeIDE\_2.2.0\\STM32CubeIDE

```



For a different installation, supply its path:



```powershell

. .\\setup.ps1 -CubeIdeRoot 'C:\\path\\to\\STM32CubeIDE'

```



The script finds the compiler, Make, and programmer inside the installation's `plugins` folder.



PATH changes apply only to the current PowerShell session. Run the setup again when opening a new session.



If multiple matching tool versions are installed, the script selects the first match after sorting paths in descending alphabetical order.



\## Build Commands



\### Build the firmware



```powershell

make -j4

```



This allows up to four build jobs to run in parallel.



\### Display firmware memory usage



```powershell

make size

```



\### Remove generated build files



```powershell

make clean

```



\### Perform a clean rebuild



```powershell

make clean

make -j4

```



Run these sequentially so cleaning finishes before compilation starts.

\## Program the Board



1\. Connect the board through the onboard ST-LINK USB connector.

2\. Stop any active debugger session using the same ST-LINK.

3\. Load the tool setup if needed.

4\. Run:



```powershell

make flash

```



This builds the ELF if needed, connects through SWD under reset, writes the firmware, verifies it, and resets the MCU.



Programming replaces the firmware currently on the board.



To specify the programmer executable explicitly:



```powershell

make flash PROGRAMMER="C:/path/to/STM32\_Programmer\_CLI.exe"

```



The `flash` target depends on the ELF. Run `make` to also update the BIN and HEX files after source changes.



\## How the Makefile Works



1\. Each file in `Src/` is compiled into a separate object file.

2\. The startup assembly is compiled into its own object file.

3\. The linker combines the objects using the flash linker script.

4\. `objcopy` generates BIN and HEX images from the ELF.

5\. Generated dependency files identify which objects depend on each header.



The Makefile uses `cmd.exe` for its Windows commands.



Recipe lines start with `>` through GNU Make's `.RECIPEPREFIX` setting, avoiding the usual requirement for tab indentation.



The build enables compiler warnings and treats compiler warnings as errors.



The firmware uses the software floating-point ABI. It does not require enabling the hardware FPU.



The `-nostartfiles` option excludes the toolchain's standard startup files because the project supplies its own MCU startup code.



\## Incremental Builds



Make compares file timestamps to determine what needs rebuilding.



| Change | Expected build behavior |

|---|---|

| No changes | No build commands run |

| Update `Src/led.c` | Recompile `led.c`, relink, and regenerate BIN/HEX |

| Update `Inc/led.h` | Recompile `led.c` and `main.c`, then regenerate firmware |

| Change the Makefile | Recompile all objects and regenerate firmware |

| Change the linker script | Relink and regenerate firmware |



Header dependencies are generated using `-MMD -MP` and included through the `.d` files.



\## Application Timing



| Parameter | Value |

|---|---|

| Assumed processor clock | Reset-default 16 MHz HSI |

| SysTick interrupt interval | Approximately 1 ms |

| Button debounce time | 20 ms |

| Slow blinking | 500 ms on, 500 ms off |

| Fast blinking | 100 ms on, 100 ms off |



The SysTick interrupt increments a volatile millisecond counter.



The main loop reads this counter to debounce the button and update the LEDs without blocking delays.



Unsigned subtraction handles millisecond-counter wraparound.

\## Limitations



\- The Makefile's shell commands target Windows.

\- The setup script assumes the STM32CubeIDE plugin directory layout.

\- Timing depends on the internal HSI oscillator and assumes a 16 MHz CPU clock.

\- Changing the clock configuration requires updating the SysTick reload value.

\- No automated hardware tests or oscilloscope timing measurements were performed.
